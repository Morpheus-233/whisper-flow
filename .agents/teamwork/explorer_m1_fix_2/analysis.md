# Deep-Dive Investigation: Devanagari Danda Punctuation Failure Modes

**Investigator**: M1 Fix Explorer 2  
**Target Repository**: `whisper-flow`  
**Focus Scope**:
1. Devanagari Danda (`।` U+0964, `॥` U+0965) token splitting in `style_engine.py:romanize`.
2. Boundary lookaround in `voice_profile.py:apply_replacements` treating danda as word characters.
3. Drop-in code modifications for implementer agents.

---

## 1. Executive Summary

Devanagari text generated by Whisper ASR often terminates clauses and sentences with Devanagari Danda (`।` `\u0964`) and Double Danda (`॥` `\u0965`). In the current codebase:
1. `style_engine.py:romanize` uses `re.split(r'(\s+|[^\w\u0900-\u097F]+)', text)` to tokenize input into words and delimiters. Because `\u0964` and `\u0965` fall within Unicode range `\u0900-\u097F`, the character class `[^\w\u0900-\u097F]+` excludes them from being matched as delimiters. As a result, the danda remains fused to the preceding word token (e.g. `'कोड।Store'`, `'पुश।Store'`). This causes dictionary lookup in `DEV_COMMON_WORDS` to fail and triggers algorithmic transliteration that treats the consonant before the danda as medial, appending an unwanted schwa `'a'` (`'koda.'`, `'pusha.'`, `'sarvara.'`).
2. `voice_profile.py:apply_replacements` constructs single-pass boundary regexes using `rb = r'(?![\w\u0900-\u097F])'`. Because `\u0964` and `\u0965` are in `\u0900-\u097F`, the negative lookahead matches the danda, classifying it as a continuation of the word. Consequently, words followed by danda (e.g. `'सर्वर।'`) fail the lookahead boundary check and personal dictionary replacements are completely blocked.

Both failures can be cleanly, deterministically resolved by excluding `\u0964` and `\u0965` from word-constituent ranges (`\u0900-\u0963\u0966-\u097F`) in both files.

## 2. Failure Mode 1: Danda Token Splitting in `style_engine.py`

### 2.1 Code Location & Mechanism
In `style_engine.py` lines 277-286:
```python
    @classmethod
    def romanize(cls, text: str) -> str:
        """Converts Devanagari script in text to natural Romanized Hinglish."""
        if not text or not cls.has_devanagari(text):
            return text

        tokens = re.split(r'(\s+|[^\w\u0900-\u097F]+)', text)
        result = ''.join(cls.transliterate_token(t) for t in tokens)
        result = re.sub(r'[ \t]+', ' ', result).strip()
        return result
```

### 2.2 Root Cause Analysis
In Python Unicode regex:
- `\w` matches alphanumeric characters and combining marks (Unicode categories `L`, `N`, `Mn`, `Mc`), including Devanagari letters (`क`, `स`) and matras (`ा`, `ि`).
- `\w` does **not** match punctuation marks (category `Po`), so `re.match(r'^\w$', '।')` is `False`.
- However, line 282 explicitly specifies `[^\w\u0900-\u097F]+`.
- The Devanagari Unicode block spans `U+0900` to `U+097F`:
  - `U+0900` to `U+0963`: Vowels, consonants, matras, virama/halant.
  - `U+0964`: Devanagari Danda (`।`) — Unicode category `Po` (Punctuation, other).
  - `U+0965`: Devanagari Double Danda (`॥`) — Unicode category `Po` (Punctuation, other).
  - `U+0966` to `U+096F`: Devanagari Digits (`०` - `९`).
  - `U+0970` to `U+097F`: Abbreviation sign, candra vowels, additional letters.
- Because `[^\w\u0900-\u097F]+` negates the **entire** block `\u0900-\u097F`, characters `\u0964` and `\u0965` are **not matched** by `[^\w\u0900-\u097F]+` and are not `\s+`.
- Therefore, `re.split` does not split at `।` or `॥`.

### 2.3 Cascading Error in `transliterate_token`
When `text = 'कोड।'`:
1. `tokens` evaluates to `['कोड।']` (a single token).
2. `transliterate_token('कोड।')` checks `if word in cls.DEV_COMMON_WORDS:`.
   - `cls.DEV_COMMON_WORDS` contains `'कोड': 'code'`.
   - `'कोड।'` is not found in `DEV_COMMON_WORDS`.
3. The method falls back to algorithmic transliteration (lines 212-270):
   ```python
   elif ch in cls.CONSONANTS:
       base = cls.CONSONANTS[ch]
       if i + 1 < n:
           nxt = word[i + 1]
           ...
           else:
               out.append(base + 'a')
               i += 1
       else:
           # Word-final schwa deletion
           out.append(base)
           i += 1
   ```
4. For consonant `ड` (`base = 'd'`), because `i + 1 < n` (the next character in the token is `'।'`), the algorithm treats `ड` as an internal/medial consonant and appends `base + 'a'` (`'da'`).
5. Then in the next iteration, `ch = '।'` matches `elif ch in ('\u0964', '\u0965'): out.append('.')`.
6. Final output: `'koda.'` instead of `'code.'`.

### 2.5 Proposed Fix for `style_engine.py`
Exclude `\u0964` and `\u0965` from the word character range in line 282:
```python
tokens = re.split(r'(\s+|[^\w\u0900-\u0963\u0966-\u097F]+)', text)
```
And add secondary defense-in-depth inside `transliterate_token` (line 243) so that even if a token containing a danda is directly passed into `transliterate_token`, word-final schwa deletion correctly triggers:
```python
                    elif nxt in ('\u0964', '\u0965'):
                        out.append(base)
                        i += 1
```

## 3. Failure Mode 2: Boundary Lookaround in `voice_profile.py`

### 3.1 Code Location & Mechanism
In `voice_profile.py` lines 218-226:
```python
        patterns = []
        for k in sorted_keys:
            lb = r'(?<![\w\u0900-\u097F])' if (k[0].isalnum() or k[0] == '_' or '\u0900' <= k[0] <= '\u097F') else ''
            rb = r'(?![\w\u0900-\u097F])' if (k[-1].isalnum() or k[-1] == '_' or '\u0900' <= k[-1] <= '\u097F') else ''
            patterns.append(lb + re.escape(k) + rb)

        reps_lower = {k.lower(): v for k, v in reps.items()}
        pattern = re.compile(r'(' + '|'.join(patterns) + r')', re.IGNORECASE)
        return pattern.sub(lambda m: reps_lower.get(m.group(0).lower(), m.group(0)), text)
```

### 3.2 Root Cause Analysis
- `lb` and `rb` are designed to protect word boundaries for both ASCII and Devanagari words.
- For a key like `k = 'सर्वर'` (or `k = 'server'`):
  - `lb = r'(?<![\w\u0900-\u097F])'`
  - `rb = r'(?![\w\u0900-\u097F])'`
- When the input string is `'सर्वर।'` (or `'server।'`):
  - The pattern attempts to match `'सर्वर'` at index 0.
  - Lookbehind `(?<![\w\u0900-\u097F])` succeeds (start of string).
  - The literal characters `'सर्वर'` match.
  - The negative lookahead `(?![\w\u0900-\u097F])` inspects the next character: `'।'` (`\u0964`).
  - Because `'\u0900' <= '\u0964' <= '\u097F'` is `True`, `'।'` matches `[\w\u0900-\u097F]`.
  - The negative lookahead fails, aborting the match.
- As a consequence, `'सर्वर'` is **never replaced**, violating the 100% dictionary match guarantee.

### 3.3 Empirical Test Failure
From `tests/test_m1_round2_adversarial.py:299`:
```

```

### 3.4 Proposed Fix for `voice_profile.py`
Exclude `\u0964` and `\u0965` from the lookaround character classes and condition checks in lines 220-221:
```python
            lb = r'(?<![\w\u0900-\u0963\u0966-\u097F])' if (k[0].isalnum() or k[0] == '_' or ('\u0900' <= k[0] <= '\u0963' or '\u0966' <= k[0] <= '\u097F')) else ''
            rb = r'(?![\w\u0900-\u0963\u0966-\u097F])' if (k[-1].isalnum() or k[-1] == '_' or ('\u0900' <= k[-1] <= '\u0963' or '\u0966' <= k[-1] <= '\u097F')) else ''
```
